# W26 Booting from UEFI  (M26)  — status: in progress
Goal: Burrow boots from UEFI firmware as well as from a BIOS, on the same nucleus and Go kernel, with the screen GOP set. Demo: QEMU with OVMF (UEFI firmware for QEMU, packaged as `ovmf`) boots `build/go-uefi.img`, a GPT disk whose EFI system partition holds `\EFI\BOOT\BOOTX64.EFI` and Burrow's payloads; the loader takes the memory map, the ACPI tables and a framebuffer from the firmware, leaves its boot services and starts the nucleus as stage2 does today; the console, Doom and the X desktop run on four CPUs and on one, and power off through ACPI; the BIOS images boot as before; a guide says how to put the image on a USB stick and what a real PC still lacks; `make test` green. Stories: E23.F01-F05 ([BACKLOG.md](../BACKLOG.md)).

Where we start (after W25): only a BIOS boots Burrow. stage1 (the MBR) loads stage2, which asks the BIOS for the memory map (E820) and a VBE mode, switches to long mode with 1 GiB identity-mapped, and calls the C loader with `boot_info` at physical 0x1000 (`include/burrow/boot_info.h`, v2 from stage2). The loader checks it, reads the manifest's payloads through its own ATA driver with their CRCs, puts the nucleus at physical 1 MiB, builds the page tables and hands over `boot_info` v3 (`loader/main.c`). The nucleus finds the ACPI tables by scanning the BIOS areas for the RSDP (`nucleus/acpi.c`), starts the other CPUs from a trampoline at 0x8000 (`smp.c`), and insists that `boot_info` is at 0x1000 (`boot.c`); the Go kernel looks for the manifest in `hda`'s sector 1 (`kernel/cmd/kernel/disks.go`). Most PCs sold in the last decade boot UEFI only, or hide the BIOS path; QEMU's default firmware is SeaBIOS, a BIOS, so none of this has been needed yet. RISKS.md R-06 has said "UEFI path later" since W0.

Design (a second front half, one back half; the nucleus barely notices):
- **The loader gets a UEFI front half beside the BIOS one.** `loader/efi/` is a UEFI application: freestanding C called with Microsoft's x64 convention (`ms_abi`, UTF-16 strings, `-fshort-wchar`), built position independent and linked by binutils' `ld -m i386pep` into a PE32+ image with base relocations (no gnu-efi, no EDK II: the few protocol structures it needs are declared in one header, `loader/efi/efi.h`). The back half the BIOS loader already has (the nucleus's ELF, the boot modules, the page tables, `enter_nucleus`) moves into `loader/handoff.c` and both front halves call it; the front half's job is to fill the same `boot_info` stage2 fills.
- **The firmware describes the machine.** The memory map comes from `GetMemoryMap` and is turned into E820 records (`loader/efimap.c`, pure and host-tested: boot-services memory is usable after the exit, runtime services and ACPI NVS stay reserved, ACPI reclaim is `E820_ACPI`); the RSDP comes from the configuration table and goes into a new `boot_info` field (v4: `rsdp_addr`; the nucleus scans the BIOS areas only when it is 0); the framebuffer comes from GOP (`fb_source` `FB_SOURCE_GOP`), its mode chosen from the image's `video` request as stage2 chooses a VBE mode.
- **The image is a GPT disk with an EFI system partition.** `tools/mkimage -uefi` writes a protective MBR, the GPT headers and table (with their CRCs) and a FAT32 partition labelled `BURROWBOOT` holding `\EFI\BOOT\BOOTX64.EFI`, the manifest as a file (`\burrow\manifest`, the same 512-byte record with its CRCs; the LBAs unused) and every payload as a file (`nucleus`, `kernel`, `initrd`, `kargs`, `ktest`, `video`). The loader reads them with the firmware's file protocol and checks each CRC as the BIOS loader does: "verify before you execute" (BUG-0003) holds on both paths.
- **The fixed addresses stay fixed where they can.** The loader claims the pages the nucleus expects (`boot_info` and E820 at 0x1000-0x2FFF, the AP trampoline at 0x8000, the nucleus at 1-4 MiB) with `AllocatePages(AllocateAddress)` and fails loudly, naming the address, when the firmware owns one; only if OVMF does is `boot_info` made movable.
- **The nucleus meets a machine the firmware set up.** After `ExitBootServices` the loader masks interrupts and hands over as stage2 would; the nucleus already loads its own GDT, IDT and page tables, but every other assumption it made about the state stage2 left (the 8259 and the LAPIC, the PIT, CR0.WP, EFER.NXE, CR4) is checked against what OVMF leaves, and written down.
- **The Go kernel knows its boot disk either way.** `hda` is a manifest disk or a GPT disk whose ESP is `BURROWBOOT`; the ESP is never mounted as a data disk, and the data disks (home, root, X, Qt, net, Doom) are found by label as before.

### [x] W26-S01 A UEFI application (E23.F01)
`loader/efi/efi.h` (the system table, boot services, the simple text output, the loaded image and the simple file system protocols, nothing more), `loader/efi/main.c` (`efi_main`: print through the firmware's console and on COM1 with `common/serial.c`, then debug-exit), built by the Makefile into `build/efi/BOOTX64.EFI` (`-ffreestanding -fpic -fshort-wchar -mno-red-zone -mgeneral-regs-only`, `ld -m i386pep --subsystem 10`), its PE header checked by a host test. `tools/mkimage -uefi` writes the GPT disk with its ESP (`tools/mkimage/gpt.go`, `esp.go`; host tests check the headers' CRCs and the backup header, and `make uefi-interop` checks the image with `sfdisk`, `mdir` and `fsck.fat` when they are installed). `make uefi-smoke` boots `build/uefi.img` with OVMF (`OVMF_CODE ?= /usr/share/OVMF/OVMF_CODE_4M.fd`, a copy of `OVMF_VARS_4M.fd` per boot) and checks `tests/smoke/expect/boot_to_efi.txt`: `[efi] hello from UEFI`.
As built: binutils' PE linker (`ld -m i386pep`) links ELF objects but writes no base relocations for them, so its image would run only where it was linked (OVMF put ours at 0x6235000). The loader is linked as a static PIE instead (`loader/efi/linker.ld`, `ld -static -pie --no-dynamic-linker`, code and data on their own pages; ld marks a PIE linked above 0 `ET_EXEC`, so the converter asks for a `PT_DYNAMIC`), and `mkimage -efi-app` (`tools/mkimage/pe.go`, `pewrite.go`) writes the PE32+ itself: a section per `PT_LOAD` at the same address, image base 0, each `R_X86_64_RELATIVE` a DIR64 base relocation, anything else refused (`TestELFToPE`, `TestELFToPERefuses`, read back with Go's `debug/pe`). `loader/efi/main.c` checks a pointer kept in data to show the relocations were applied. The boot partition: `mkimage -esp-dir` writes its files (`esp.go`: the loader, `burrow/manifest` with the BIOS layout's entries, each payload under `burrow/`), `kernel/cmd/mkfat` makes the FAT32 volume (`BURROWBOOT`, 34 MiB, FAT32's least), `mkimage -gpt` wraps it (`gpt.go`, `TestBuildGPT`: CRCs, the backup header and table, reproducible GUIDs from the partition's hash); the Makefile's `uefi_image` does the three. `smoke.sh` boots OVMF when `OVMF_CODE`/`OVMF_VARS` are set (a fresh copy of the variables each boot); OVMF's own lines on COM1 (screen clears, `BdsDxe: loading Boot0001 ...`) contain no `FAIL`. `tests/regression/uefi_interop.sh` (`make uefi-interop`): `sfdisk` (which quietly uses the backup when the primary header is bad, so its warning fails the check), `fsck.fat`, `mdir`/`mlabel` at `@@1M`, `objdump -p`. Both are in `make test`; CI installs `ovmf`.

### [x] W26-S02 The machine from the firmware (E23.F02)
`loader/efimap.c` (pure, in `UNIT_SRC`): UEFI memory descriptors to E820 records, merged and sorted, with host tests over maps taken from OVMF; the RSDP from the configuration table (ACPI 2.0's GUID first, 1.0's after); the fixed pages claimed (and a refusal that names the address: `REG-NNNN-efi-page-taken` through a kargs-free mutator, the loader asked to claim a page OVMF owns); the manifest file and every payload read from the ESP into a frame pool below 1 GiB, each CRC checked (`REG-NNNN-efi-payload-crc`: a payload file flipped in the ESP). `boot_info` v4 adds `rsdp_addr` (mirrors in `boot/boot_abi.inc`, `kernel/bootinfo`, `BOOT_PROTOCOL.md`, `MEMORY_MAP.md`; `_Static_assert`s and `TestParseBootInfo`); stage2's path sets it to 0. `boot_to_efi.txt` gains `[efi] memory map ok`, `[efi] acpi rsdp at ...`, `[efi] manifest ok` and each payload's `crc ok`.
As built: OVMF leaves 0x1000-0x2FFF, 0x8000 and 1-4 MiB free (`[efi] claimed ...`), so `boot_info` stays at 0x1000; the regression case claims the loader's own first page instead (`burrow/efitest` asks for it; REG-0011: `[efi] PANIC: the firmware owns ...`), and REG-0010 changes `burrow/nucleus` inside the partition with mtools (`run_all.sh`'s `REG_UEFI=1` boots OVMF; both skip without OVMF or mtools). `loader/efi/` grew `efi_loader.h`, `firmware.c` (claims, pages below 1 GiB, the map, the RSDP) and `files.c` (the volume the loader came from, `burrow/manifest` and the payloads, one byte more read than the manifest says so a longer file shows); the UEFI build links `loader/manifest.c` and `memmap.c`. `efimap.c` (pure, `test_efimap.c`): OVMF's 126 descriptors on 128 MiB become 20 records, 121 MiB usable. `boot_info` v4 puts `rsdp_addr` at 0x68 (`reserved` is two words at 0x70; `FB_SOURCE_GOP` 2 named for S04); the BIOS loader writes 0 there, the markers became `boot_info v4 ok` (as W21-S02 moved them from v2 to v3), `kernel/bootinfo` reads `RSDP` and refuses a version 3. `BURROW:EFI:OK` now follows the start-up checks and `[efi] payloads ok` ends the slice's boot; the expect file only grew. The S01 Makefile lines written through a heredoc had lost their continuations (three joined lines); restored.

### [x] W26-S03 Leave the firmware, start the nucleus (E23.F03)
The back half shared: `loader/handoff.c` (the nucleus's ELF into the claimed 1 MiB window, boot modules, page tables, `boot_info` v4, `enter_nucleus`) used by `loader/main.c` and `loader/efi/main.c`, with the BIOS images' markers unchanged. `ExitBootServices` with the last map's key (taken after the last allocation and the last print; one retry on `EFI_INVALID_PARAMETER`), then `cli`, then the hand-off; the identity map covers the loader wherever the firmware put it. The nucleus takes the RSDP from `boot_info` when it is set (`acpi.c`), and its start-up is audited against OVMF's state (the 8259 and LAPIC modes, the PIT, CR0/CR4/EFER; what it found goes into BOOT_PROTOCOL.md). `make uefi-smoke` reaches `BURROW:NUCLEUS:OK` on `uefi.img`, and the ktest suites run under OVMF on one CPU and four (`make uefi-ktest`: `mm`, `sched`, `smp`, `irq`).
As built: `loader/handoff.c` (`struct handoff`: a marker tag, a `palloc`, the map, the loader's pages, the modules) holds what `loader/main.c` did from the nucleus's segments to the jump; the jump is `cpu_enter_space` in `common/cpu.h` (`entry.asm`'s `enter_nucleus` is gone) and the BIOS markers are unchanged. `vm_plan` gained `loader_base`/`loader_bytes` (identity pages above 1 GiB only; `vm_build_maps_the_loader`), `acpi_mem` `rsdp_pa` (`acpi_rsdp_from_firmware`). The UEFI loader's page tables come from one block (32 pages plus two per GiB of physmap) palloc treats as its only RAM; `efi_leave_boot_services` (`firmware.c`) takes its buffer first and converts the last map without printing. OVMF's state needed nothing from the nucleus (BOOT_PROTOCOL.md lists it); all four CPUs came up on the first boot. `uefi-smoke` boots twice, the second with 2 GiB, where OVMF puts the loader near 2 GiB (at 3 GiB, near 3 GiB: tried by hand). `make uefi-ktest` is in `make test`.

### [ ] W26-S04 The screen from GOP (E23.F04)
The loader finds the graphics output protocol, picks the mode the `video` payload asks for (else the firmware's current one), sets it and fills the framebuffer fields with `fb_source` `FB_SOURCE_GOP` (its pixel formats: RGB and BGR with 8 reserved bits, a bit mask, or blit-only, which gives no framebuffer and leaves DISPI to the Go kernel); `nucleus/fbdesc.c` accepts it (host tests for each format). The Go images get UEFI twins (`go-uefi.img`, from the same payloads); the Go kernel recognises a GPT boot disk (`hda: GPT, boot partition "BURROWBOOT"`) and mounts the data disks as before. Messages on the screen before the Go console: once GOP has set a mode, the loader's and the nucleus's lines (and above all a panic) are drawn on the framebuffer too, in the 5x8 font of `kernel/gfx/font.go` (a C copy beside it, a pure text-to-cells module host-tested), because a real PC rarely has a serial port and a photo of the screen is the report a tester can send. `make uefi-smoke` also boots `go-uefi.img` to the console (`boot_to_go_uefi.txt`), checks the screen's pixels at the GOP mode, and powers off through ACPI with the RSDP the firmware gave.

### [ ] W26-S05 Everything on UEFI, and a USB stick (E23.F05)
The demos on UEFI: Doom (`go-doom-uefi.img`, pixels checked), the X desktop on the ext2 root as burrow (`go-unix-uefi.img`), the network; `make uefi-smoke` covers them, halves skipping without their ports, on `-smp $(SMP)`. `UEFI=1` on the run targets boots their UEFI twins (`make run-unix UEFI=1`). `make uefi-usb` writes `build/burrow-usb.img` (the desktop image with its disks' partitions on one GPT disk, so a single stick carries the root and the data volumes, found by label); `docs/06-guides/REAL_HARDWARE.md` says how to write it to a stick, that Secure Boot must be off, and what a real PC is likely to lack today (an IDE or PS/2 controller, an e1000: the I/O APIC and MSI, AHCI, NVMe, USB keyboards and mice, and USB storage are W27's), and to write the image with `dd` or Rufus's DD mode rather than Ventoy (Ventoy boots an image as a file, so the kernel finds none of its partitions). `make test` runs `uefi-smoke`.

Exit: **M26 demo — booting from UEFI.** `make uefi-smoke` boots the nucleus, the Go console, Doom and the desktop under OVMF on four CPUs and on one, with GOP's framebuffer and ACPI from the firmware's tables; every BIOS image boots as before; `make uefi-usb` writes a stick image and REAL_HARDWARE.md says what to expect; `make test` green on both CPU counts; DEVLOG wave entry.

Not in this wave: drivers a real PC needs that QEMU's `pc` machine does not (the I/O APIC and MSI, AHCI, NVMe, xHCI with USB keyboards, mice and storage; the `q35` machine: W27, [WAVE-27](WAVE-27-real-pc.md)), Secure Boot and signing, UEFI runtime services (`SetVirtualAddressMap`, the firmware's clock or variables: the CMOS clock and ACPI stay), a boot menu or chain-loading, booting from CD (El Torito), a 32-bit UEFI, proving a boot on a particular PC (the guide asks for reports).

Risks and pitfalls (PIT-NN entries go into BUGS_AND_MITIGATIONS.md when the wave starts):
- **The firmware may own the fixed addresses.** OVMF uses low memory for its own data; if 0x1000, 0x8000 or the 1 MiB window is taken, `AllocatePages(AllocateAddress)` fails. The loader says which, and the fix (a movable `boot_info`, a trampoline the nucleus copies to a page the loader found) is made only then.
- **`ExitBootServices` wants the latest map's key.** Any allocation, and on some firmware a print, changes the map; the map is taken last, nothing is printed between it and the call, and a stale key is retried once with a fresh map.
- **Two conventions in one program.** Firmware calls are Microsoft x64 (`ms_abi`: other argument registers, shadow space, a 16-byte aligned stack), strings are UTF-16, and the PE image is relocated wherever the firmware loads it; a wrong attribute or a missing relocation works by luck under one firmware and faults under another. A host test checks the PE header and relocations; the loader's own CRC check is the BIOS path's alone.
- **The firmware leaves the machine in its own state.** Interrupts on, the LAPIC enabled, the 8259 possibly masked or remapped, its own GDT, IDT and page tables (with NX and CR0.WP set), the PIT running; the nucleus's start-up assumed stage2's state. Each difference is found with a ktest under OVMF, not by luck.
- **Firmware text on the serial line.** OVMF prints to COM1 before the loader does; the smokes fail on any line containing `FAIL` or `PANIC`, so the firmware's output is checked once and the smoke reads only from the loader's first line if it must.
- **The boot disk is FAT now.** The ESP is a FAT32 volume and the Go kernel mounts FAT volumes it finds; it must tell the boot partition from a data disk, or `/mnt` becomes the boot files.
- **OVMF is slow on TCG.** The firmware takes seconds to reach the loader under emulation; the UEFI smokes get their own timeouts, and `make test` grows by the UEFI boots (kept to one per demo).
