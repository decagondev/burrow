# W21 A Firmware Framebuffer  (M21)  — status: in progress
Goal: Burrow gets its framebuffer from the firmware, the way real hardware forces it to, instead of from the Bochs/QEMU DISPI registers, and the stack above it stops assuming 1024x768, a tight pitch and XRGB. This is the rehearsal, in QEMU, of the one bare-metal bring-up step BGA has let us skip. Demo: stage2 sets a linear VBE mode through the BIOS and records it in boot_info; `[nucleus] framebuffer 1280x1024x32 pitch 5248 at fd000000 (vbe)`, a pitch that is not width times four, on purpose; the console, `/dev/fb0` programs, Doom, Qt and X draw correctly at that geometry; `make fb-smoke` boots the odd mode and checks pixels; the framebuffer is mapped write-combining; `make test` green, with the DISPI path still serving images that ask for no mode. Stories: E02.F04.S01, E07.F04.S01-S04 ([BACKLOG.md](../BACKLOG.md)).

Where we start (after W20): `kernel/drivers/bga` sets 1024x768x32 through the DISPI registers (ports 0x1CE/0x1CF; `bga.Width`, `Height`, `BPP` are constants), reads the pitch the card settled on, finds the linear framebuffer in the PCI BAR, and maps it with `nu_mmio_map` (uncached and NX, physmap + pa; NUCLEUS_ABI.md). `kernel/gfx` is already pitch-aware (`Stride`, PIT-27) but packs XRGB8888 only. `fbdev` reports `line_length` and the colour fields, and every program that draws on `/dev/fb0` already steps rows by `line_length`: `user/fbtest.c`, `user/paint.c`, the Doom backend (`user/doom/doomgeneric_burrow.c`, which also centres and scales by `xres`/`yres`), Xfbdev and Qt's linuxfb. boot_info already has `fb_addr`, `fb_width`, `fb_height`, `fb_pitch` and `fb_bpp` at 0x30-0x47, zero today ("until a later wave fills it"), and 32 bytes of `reserved` at 0x60; `boot/boot_abi.inc` has no `BI_FB_*` names yet, and the Go mirror is `kernel/bootinfo` (with its layout test), not `tools/mkimage`. stage2 has a 32-sector (16 KiB) slot; the loader and the nucleus print to serial only. The loader's physmap covers RAM below 4 GiB, so the framebuffer BAR (QEMU: 0xfd000000) is mapped once, by `nu_mmio_map`. Every `tests/smoke/expect/*.screen` file checks `size ... 1024 768`, and the desk and X keys files move the mouse in 1024x768 pixels: those smokes must keep that mode. On real hardware there is no DISPI device: a linear framebuffer comes from VBE (a legacy BIOS, or UEFI's CSM) or GOP (UEFI), and an uncached one turns every pixel into a bus transaction. This wave does VBE in SeaBIOS, makes geometry and pixel format a boot_info contract, and maps the framebuffer write-combining; GOP and real silicon come later.

Design (mechanism in stage2 and the nucleus, geometry as a contract, policy in Go):
- **The image says which mode it wants.** A small binary manifest payload, `video` (width, height, bpp, and an optional pitch in bytes), built by `tools/mkimage` from a flag; stage2 looks for it. An image without one (`disk.img`, the ktest images) does no VBE at all, leaves the descriptor zero, and the Go kernel falls back to DISPI exactly as today. The Go images ask for 1024x768x32, so every existing screen check holds; `fb-smoke`'s image asks for the odd mode.
- **The mode is set in real mode, last.** stage2 walks the VBE mode list (`AX=4F00` with `"VBE2"` for the controller info and `VideoModePtr`, `AX=4F01` for each `ModeInfoBlock`), takes a linear direct-colour mode with the requested width, height and bpp, sets it (`AX=4F02`, `BX=mode|0x4000`), then, if a pitch was asked for, sets the logical scan line in bytes (`AX=4F06 BL=02`) and reads back what the card took (`BL=01`). That is the only way to get a padded pitch out of QEMU: its std-vga VBE modes are tight (`BytesPerScanLine = width*4`). This happens just before the protected-mode switch; the serial marker goes out first.
- **The framebuffer is a boot_info contract.** stage2 fills the existing `fb_*` fields and a pixel layout in the reserved space (red, green and blue field positions and sizes, a source byte: none, VBE; the rest stays reserved), so nothing above it knows about VBE. The fields do not move; both versions bump (stage2 writes 2, the loader 3) so a mixed image fails at the loader's version check, loudly. Mirrors: `include/burrow/boot_info.h` (`_Static_assert`s), `boot/boot_abi.inc` (new `BI_FB_*`), `kernel/bootinfo` and its layout test; MEMORY_MAP.md and BOOT_PROTOCOL.md.
- **gfx believes the descriptor.** The Go kernel takes geometry, pitch and pixel format from boot_info when the source says VBE; the pixel packer honours the field positions; `drivers/bga` sets a DISPI mode only when there is no descriptor, and otherwise adopts it (the BAR it already finds must match `fb_addr`, or it says so).
- **Write-combining is the nucleus's job.** The loader does not stay resident and does not map device memory; `nu_mmio_map` does. The nucleus programs the PAT MSR on every CPU at start-up, the BSP and each AP alike (the SDM wants the same PAT everywhere, and W20 brought the APs), with one entry WC, and a new `nu_mmio_map` flag maps a range with that entry; uncached stays the default and the fallback without PAT. A physical range must never have two mappings with different memory types: the framebuffer is mapped once, and the physmap does not reach it.
- **Odd geometry is the test, not an accident.** QEMU will hand us tidy modes if we let it; `fb-smoke` asks for 1280x1024x32 with a 5248-byte pitch, so any `pitch == width*4` or 1024x768 assumption left anywhere shows up as a screendump difference in the emulator.

### [x] W21-S01 A VBE mode set in stage2 (E02.F04.S01)
The `video` payload: `tools/mkimage -video WxHxB[,pitch]` writes it (a fixed little struct with a magic, mirrored like the manifest, with a Go test). stage2: if the manifest has it, real-mode VBE before the protected-mode switch: the controller info and mode list (`4F00`, `"VBE2"` in, `"VESA"` back), each candidate's `ModeInfoBlock` (`4F01`: attributes linear and graphics, memory model direct colour, `XResolution`, `YResolution`, `BitsPerPixel`, `PhysBasePtr`, `BytesPerScanLine`, the colour fields), the first exact match set with the linear bit (`4F02`), then `4F06` for a requested pitch, read back. The info blocks live in a scratch area below 1 MiB named in MEMORY_MAP.md (the free 0x80000 range is the loader's stack later; the info is copied out first). Captured values go to a fixed spot for S02. Markers: `[stage2] vbe: 1024x768x32 pitch 4096 at fd000000 (mode 0x118)` before the switch, or `[stage2] vbe: no 1280x1024x32 mode` and nothing set (the image still boots, on DISPI). Check `make sizes` before and after: stage2 has a 16 KiB slot and VBE costs a few hundred bytes. Text output after the mode set: stage2's own messages go to serial only from there (audit the paths after it); the loader and the nucleus are serial-only already. Every Go image gets `-video 1024x768x32`; `disk.img` and the ktest images get none.
As built: `tools/mkimage/video.go` (`ParseVideo`, `MarshalBinary`, tests against the C layout) and `-video`; `struct video_request` in `include/burrow/manifest.h` with `_Static_assert`s, `VR_*` and the scratch addresses in `boot_abi.inc`. `boot/vbe16.inc` holds stage2's VBE code and its COM1-only output (`sputc`, `sprint`, `sdec`, `shex`); stage2's manifest lookup became `find_entry`, shared by the loader and the video payload; `vbe_setup` runs right after `[stage2] entering protected mode`, the last BIOS teletype output, so the marker goes out after the mode set, on COM1 (which a graphics mode does not touch), and can print the pitch the card accepted. Scratch at 0xC000-0xC5FF, between the stage2 slot and the loader (the free 0x80000 range would have needed a segment register for every access). The Go images get `-video $(VIDEO)` (`VIDEO ?= 1024x768x32`, through `MKIMAGE_GO`): `[stage2] vbe: 1024x768x32 pitch 4096 at fd000000 (mode 0x144)` is now in `boot_to_go`, and the Go kernel's DISPI mode set still follows (S03 stops that). `make vbe-smoke` (in `make test`) boots the nucleus image asking for `1280x1024x32,5248` (`pitch 5248`: SeaBIOS's vgabios does honour 4F06, so QEMU can give a padded pitch) and for `1000x700x32` (`no 1000x700x32 mode`, boots on). By hand: `800x600x16,1700` came back as 1696, so the card rounds and the read-back matters. Corrupt payloads and a listed mode that refuses to set fail with `[stage2] FAIL V`. The loader reads `video` like any payload, so it also reaches the Go kernel as a 16-byte boot module. stage2 grew from 1502 to 2056 of 16384 bytes.

### [x] W21-S02 The descriptor in boot_info (E07.F04.S01)
stage2 fills `fb_addr`, `fb_width`, `fb_height`, `fb_pitch`, `fb_bpp` and the new layout bytes in `reserved` (red, green, blue offset and size, `fb_source` 0 none / 1 VBE); `BOOTINFO_VERSION_STAGE2` becomes 2 and `BOOTINFO_VERSION` 3. Mirror it in `boot_info.h` (new `_Static_assert`s), `boot_abi.inc` (`BI_FB_*`), `kernel/bootinfo` (fields, layout test against the C offsets) and the docs (MEMORY_MAP.md for the framebuffer range and the VBE scratch, BOOT_PROTOCOL.md for the fields and versions). The nucleus prints `[nucleus] framebuffer 1024x768x32 pitch 4096 at fd000000 (vbe)`, or `[nucleus] framebuffer: none (dispi fallback)`, which `boot_to_nucleus` gains (disk.img asks for no mode). Host tests: a C unit test of the descriptor checks (a zero or unaligned base, a pitch below width times bytes per pixel, a format that is not 15/16/24/32 bpp: treated as "none" with a reason). Regression: `REG-NNNN-vbe-no-mode`, a go.img whose `video` payload asks for a mode that does not exist, must boot with `framebuffer: none (dispi fallback)` and the console on DISPI, not draw through address 0.
As built: `boot_info.h` gives the reserved space at 0x60 to `fb_red_size`, `fb_red_pos`, `fb_green_size`, `fb_green_pos`, `fb_blue_size`, `fb_blue_pos` (VBE's order, so stage2 copies the six bytes with one `rep movsb`), `fb_source` (0 none, 1 VBE) and a spare byte, with `reserved[3]` after; new `_Static_assert`s pin 0x38, 0x40, 0x44, 0x60, 0x66 and 0x68. `BOOTINFO_VERSION_STAGE2` is 2 and `BOOTINFO_VERSION` 3; the loader and nucleus markers say `v3` (a deliberate marker change, BOOT_PROTOCOL.md). `vbe16.inc`'s `vbe_to_bootinfo` fills the fields right after a mode is set (`BI_FB_*` in `boot_abi.inc`). `nucleus/fbdesc.c` (pure, in `UNIT_SRC`; `tests/unit/c/test_fbdesc.c`: QEMU's XRGB with a padded pitch, BGR, RGB565, 24 bpp, and a zero or unaligned base, a zero side, 1 GiB, 8 bpp, a short pitch, overlapping, outside or empty fields) checks the descriptor in `boot_init`; a refused one is cleared (`fb_source` 0) so Go falls back to DISPI as with none. `kernel/bootinfo` parses `Framebuffer` (version 3; a layout test writes the C offsets by hand). Markers: `[nucleus] framebuffer: none (dispi fallback)` in `boot_to_nucleus`, `[nucleus] framebuffer 1024x768x32 pitch 4096 at fd000000 (vbe; red 8@16 green 8@8 blue 8@0)` in `boot_to_go`, and the 1280x1024 one with pitch 5248 in `vbe-smoke`. mem-smoke's hang guard went from 300 to 480 s: on four CPUs (W20-S08) the whole run sat at the old limit with memtest at 81-84 s (63 s when S08 measured it, 56 s on one CPU), so the four-CPU page-fault path is still about 1.5 times slower than one CPU's, which is worth a look later. Regression `REG-0009-vbe-no-mode`: go.img asking for 1000x700x32 says `framebuffer: none (dispi fallback)` (the Go side's DISPI use is already today's path; S03 makes it the fallback). stage2: 2120 bytes.

### [x] W21-S03 gfx and fbdev believe the descriptor (E07.F04.S02)
`kernel/bootinfo` hands the descriptor to `drivers/bga` (renamed in its doc comment: "the display", DISPI only as the fallback): with a VBE descriptor it maps `fb_addr` for `fb_pitch * fb_height` bytes and builds `gfx` from the descriptor's width, height and stride; without one it sets DISPI as today. `bga.Width`/`Height` stop being constants (`bga.Screen()` and `bga.Phys()` already carry the rest; `kernel/cmd/kernel/screen.go`'s callers follow). `gfx` gets a pixel format (field offsets and sizes) and packs `color.Color` by it, XRGB8888 as the fast path; `fbdev` reports the descriptor's `xres`, `yres`, `line_length`, `smem_len` and colour fields. The console grid follows the geometry (columns and rows from width and height and the 5x8 font). Go unit tests (host): a 1000x700 framebuffer with a padded stride, a BGR and a 16-bpp RGB565 format (layouts QEMU's std-vga never produces), each drawn and read back against a known pattern; `kernel/hostsim` boots its console on an odd geometry. On Burrow, every existing smoke still passes at 1024x768 from VBE.
As built: `kernel/gfx` works over the device's bytes now (`Framebuffer.Mem`, `Pitch` in bytes, a `Format`), with the `[]uint32` view (`Pix`, `Stride`) kept as the fast path for 4-byte pixels; `format.go` has `Format`/`Field`, `XRGB8888` (packing is free for it), `FormatFor`, `Pack` and `Unpack` (fields widened back to 8 bits by repeating their top bits); the console scrolls by copying rows of bytes. `drivers/bga` is the display: it probes true for a firmware framebuffer on any adapter or for the Bochs adapter, takes `driver.Env.Framebuffer` (new; `bootModules` returns it) when its layout is one gfx draws (`FirmwareMode`), warns if the BAR differs and uses the firmware's address, and sets DISPI's 1024x768x32 only without one; `bga.Width`/`Height` became `DispiWidth`/`DispiHeight`, and `bga.Current()` gives the whole mode. Its line says which: `[bga] INFO: 1024x768x32 linear framebuffer at 0xfd000000 (pitch 4096, vbe)`. `fbdev.Mode` carries `BitsPerPixel` and `Red`/`Green`/`Blue` channels (zero means XRGB8888, as before) for `FBIOGET_VSCREENINFO` and the `FBIOPUT_VSCREENINFO` check. The console grid already followed the geometry (`NewConsole` divides the area by the cell). Host tests: `gfx/format_test.go` draws on a 1000x700 screen with 13 bytes of padding a row in XRGB8888, BGR8888, RGB565 and RGB888 and reads back the bytes each layout stores, then scrolls a console in RGB565, padding untouched; `bga` maps a firmware BGR mode with no Bochs adapter and refuses an 8 bpp layout; `fbdev` reports RGB565. On Burrow every smoke passes at 1024x768 from VBE; booted by hand at `1280x1024x32,5248`, the console fills the taller screen without shear and fbtest's bars (`line_length 5248`) are straight (fb-smoke makes it a test in S05). `kernel/hostsim` has no framebuffer, so its odd-geometry check is the gfx host test instead. The slice's first four-CPU `make test` also caught BUG-0023 at last, with its W20-S01 dump: two kills of one thread at once (a late request's and exit's) left the second `thread_join` waiting on a freed slot; `System.handle` no longer kills late, a second `uthread_kill` only waits, and `thread_join_id` lets one joiner reap (`T_REAPING`); `TestBUG0023LateRequestDoesNotKillAgain` and ktest `bug0023_join_twice`.

### [ ] W21-S04 A write-combining framebuffer (E07.F04.S03)
`nucleus/pat.c`: CPUID PAT check, the PAT MSR (0x277) written on the BSP and on each AP during their start-up, with entry 1 changed from WT to WC (the rest as at reset, so PCD/PWT-only mappings keep their meaning); `nu_mmio_map` gains a flags argument (`NU_MMIO_WC`; NUCLEUS_ABI.md) and `vm_map_mmio` picks the PAT/PCD/PWT bits for WC, falling back to uncached without PAT; `drivers/bga` asks for WC. ktest (mm suite, and smp so every CPU is checked): the PAT MSR reads back the same on every CPU, and a WC mapping's leaf has the WC index while other MMIO stays UC. Marker: `[nucleus] pat ok (wc at index 1)`. A throughput number cannot prove WC here: QEMU's TCG ignores memory types, so a fill runs at the same speed either way. `make fb-bench` (not in `make test`) still times a full-screen fill and a scroll from a user program on `/dev/fb0` and prints them, as a baseline for real hardware or KVM, with no budget. MEMORY_MAP.md marks the framebuffer WC.

Docs: a "Framebuffer and firmware" section in ARCHITECTURE.md (VBE, the descriptor, WC, the DISPI fallback), a note in DESKTOP.md and PORTING.md (draw by `line_length`, never assume the mode), the ROADMAP's M21 marked done, the DEVLOG wave entry.

Exit: **M21 demo — a firmware framebuffer.** stage2 sets a linear VBE mode through the BIOS; the console, `/dev/fb0` programs, Doom and X draw at 1280x1024 with a 5248-byte pitch taken from boot_info; the framebuffer is mapped write-combining on every CPU's PAT; images that ask for no mode still come up on DISPI; `make test` green (`make fb-smoke` included); DEVLOG wave entry.

Not in this wave: GOP and UEFI boot (needs a UEFI stub), real hardware, switching modes at run time (`FBIOPUT_VSCREENINFO` stays refused), double buffering or page flipping, acceleration, a second display, EDID and choosing a mode from the monitor, VBE on anything but a legacy BIOS or CSM, a WC benchmark budget (TCG cannot show one).

Risks and pitfalls (PIT-NN entries go into BUGS_AND_MITIGATIONS.md when the wave starts):
- **The mode set ends text output.** After `4F02` there is no VGA text until Go's `gfx` paints; everything between is serial only. The mode is set last in stage2, the marker goes out before it, and nothing after it may print to the screen through the BIOS.
- **QEMU's VBE pitch is always tight.** Asking for an odd resolution alone proves nothing about strides; the padded pitch comes from `4F06`, and stage2 must read back what the card accepted (the card may round it). If SeaBIOS's vgabios refuses `4F06` for a mode, fb-smoke must fail, not pass on a tight pitch: the marker prints the pitch it got, and the screen check's edge pixels depend on it.
- **Pixel format is not always XRGB.** The `ModeInfoBlock`'s colour fields exist for BGR and 16/24-bpp modes that real cards have and QEMU's std-vga does not; the packer honours them, and only host tests can cover those layouts.
- **One memory type per physical range.** A WC framebuffer that is also reachable through a WB or UC mapping (the physmap on a machine whose RAM reaches the BAR, a second `nu_mmio_map` with other flags) is undefined behaviour on real hardware and invisible in QEMU. The mapping is made once; `vm_map_mmio` refuses a second one with a different type instead of returning `PT_ALREADY_MAPPED` quietly.
- **The PAT must match on every CPU.** W20 starts the APs; each programs the same PAT before it maps anything, and a ktest reads it back everywhere.
- **boot_info version skew.** stage2, the loader, the nucleus and Go each read the block; a half-updated mirror can pass the C asserts and still misread the base in Go. Both version numbers bump, the loader refuses a mismatch, and `kernel/bootinfo`'s layout test pins the new offsets.
- **The DISPI fallback must stay a real path.** Images without a `video` payload, and those whose mode does not exist, come up on DISPI; `boot_to_nucleus` and the regression case keep it honest.
- **stage2's budget.** 16 KiB, already holding A20, E820, the manifest, CRC, paging and long mode; VBE needs a few hundred bytes plus a scratch area below 1 MiB that the loader does not reuse before the values are copied out. `make sizes` in every slice.
