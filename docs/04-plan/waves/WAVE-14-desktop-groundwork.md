# W14 Desktop Groundwork  (M14)  — status: in progress

Goal: give graphical programs what they expect from a Linux kernel below the toolkit: memory, a mouse, Unix sockets, file mappings, a clock, and the small calls toolkits make at start-up. Demo: on `go-desk.img`, `paint` (a musl program) draws on `/dev/fb0` and follows the mouse; its pen colour comes over a Unix socket from a second process, which picks it with the keyboard. Stories: E14 ([BACKLOG.md](../BACKLOG.md)).

Where we start (after W13): `/dev/fb0` and `/dev/input/event0` (keyboard only) speak Linux, threads, epoll and eventfd work, and Doom runs at about 100 fps. But QEMU gives the guest 128 MiB, the PS/2 driver throws mouse bytes away ([ps2.go](../../../kernel/drivers/ps2/ps2.go)), there are no sockets of any kind, `mmap` of a regular file is `-ENODEV`, `select` is missing, `pipe2` ignores `O_NONBLOCK`, there is no `/dev/urandom`, and every clock is time since boot.

Why this order: Wave 15 ports Qt onto `/dev/fb0` (no X server), and the waves after it bring an X server (TinyX `Xfbdev`, then dwm and st) and, later, GTK. Every one of them needs this wave; X needs all of it, Qt on linuxfb needs everything but the named sockets. See the research summary in the DEVLOG entry that planned this wave.

Design (continues W9-W13: mechanism stays in the nucleus, policy in Go; the nucleus changes only if S01 finds a limit there):
- **Linux semantics, tested on Linux first.** Every new call gets a musl test program in `user/` that is run on the host before it runs on Burrow, as `fbtest` and `evtest` were in W11. The `unimplemented syscall` log stays the to-do list.
- **The mouse is a second evdev device,** `/dev/input/event1` (relative motion, wheel, three buttons) next to the keyboard's `event0`, plus `/dev/input/mice` (the ImPS/2 byte stream older programs read). Both answer the `EVIOCGBIT` queries programs use to tell a keyboard from a mouse. QEMU's monitor (`mouse_move`, `mouse_button`) drives it in smoke tests.
- **Sockets are Go objects like pipes.** `AF_UNIX` stream and datagram sockets live in `kernel/proc` next to `pipe.go`, are `Poller`s (so `poll`, `select` and epoll work on them unchanged), and named ones appear as socket nodes in a writable mount (`/tmp`). `AF_INET` stays `-EAFNOSUPPORT` until networking (E12).
- **File mappings are copies.** `MAP_PRIVATE` of a regular file is an area (W12's demand-zero areas) whose pages are filled from the file at first touch instead of with zeros. Read-only `MAP_SHARED` behaves the same; writable `MAP_SHARED` of a file stays `-ENODEV` until a page cache exists. This is also what a dynamic loader needs later.

### [x] W14-S01 More memory (E14)
QEMU gets `-m $(MEM)` with `MEM ?= 512M` for the Go images (the nucleus-only images stay at 128 MiB). Check every place that assumes less: the loader's 1 GiB identity map (boot modules must stay below it), the PMM over E820 above 1 GiB and above the PCI hole (QEMU puts RAM past 3.5 GiB at 4 GiB), the physmap's size, and Go's `nu_page_alloc`. A ktest or user program touches 400 MiB on a 512 MiB guest and 1.5 GiB on a 2 GiB guest; both pass, and running out of memory gives `-ENOMEM` (not a panic) and a logged kill.
As built: `GO_MEM ?= 512M` for every Go image (`make` targets, and `MEM` for `smoke.sh`). Boots at 512 MiB, 2, 4 and 6 GiB all worked, and the PMM already took RAM above 4 GiB. Two real problems: (1) the physmap mapped `[0, top of RAM)`, so with more than 3 GiB it covered the PCI hole, and device memory (the framebuffer, the LAPIC) was mapped as cached RAM, where `vm_map_mmio` then found it already mapped; `loader/vmsetup.c` now maps RAM below 4 GiB up to its top and only the usable ranges above 4 GiB (host test `vm_physmap_skips_the_pci_hole`; a 6 GiB guest's physmap is 6144 MiB, not 7168). (2) A process that touched the last free frame left none for the Go kernel's next page, and the nucleus panicked. `nu_page_alloc` now keeps `USER_RESERVE_FRAMES` (32 MiB) for the kernel, `Mem.FaultIn` reports `FaultNoMem`, and the process is killed with `SIGKILL` (status 137) and `pid N (prog) killed: out of memory at ...`; its frames come back. `-ENOMEM` reaches a program only where a call allocates (`fork`, a copy into unbacked memory): mappings are reserved lazily, as on Linux, so running out shows as the kill. On the way, BUG-0014: every system call took 2 ms. `user/memtest.c` and `user/syslat.c`; `make mem-smoke` (2 GiB guest, about 2.5 minutes: 1.5 GiB touched and checked, `memtest oom` killed at about 1.9 GiB, then 1.5 GiB again). Checked by hand, not in `make test`: 4.5 GiB on a 6 GiB guest, so pages above 4 GiB.

### [x] W14-S02 A PS/2 mouse (E14)
`drivers/ps2`: enable port 2 and IRQ 12 in the 8042, reset the mouse, turn on IntelliMouse mode (sample rates 200, 100, 80, then read the id) so the wheel works, enable reporting; a decoder for 3- and 4-byte packets with sync recovery (bit 3 of byte 0), host-tested against `haltest.Fake8042`. `kernel/evdev` gets a mouse device: `/dev/input/event1` (`EV_REL` `REL_X REL_Y REL_WHEEL`, `EV_KEY` `BTN_LEFT BTN_RIGHT BTN_MIDDLE`, `EV_SYN`) and `/dev/input/mice` (ImPS/2 bytes). Both evdev devices answer `EVIOCGBIT` (event types and per-type codes), `EVIOCGPROP` and `EVIOCGKEY`. `sendkeys.py` gains `mouse <dx> <dy>` and `click <button>` steps. A `mousetest` program draws a cursor on `/dev/fb0`; a screen check finds it where the smoke test moved it.
As built: `drivers/ps2/mouse.go` (`InitMouse`: port 2 test and enable, defaults, the 200/100/80 handshake, `0xF2` reads id 3, reporting on, IRQ 12 in the config byte; `MouseDecoder`: 3- or 4-byte packets, sync on bit 3, overflowed moves dropped, screen directions out). Both IRQ goroutines drain the one data port under a mutex and route by the aux bit; no mouse is a warning, not an error. `driver.Env.Mouse` carries packets to `kernel/evdev`, which now shares a `core` (open files, held keys, identity) between the keyboard and `Mouse` (`mouse.go`), answers `EVIOCGBIT` (types, then codes), `EVIOCGKEY`, `EVIOCGPHYS`, and empty `EVIOCGPROP`/`EVIOCGLED`/`EVIOCGSND`/`EVIOCGSW` (`ioctl.go`), and has `Mice` (`mice.go`): Linux mousedev's byte stream, answering PS/2 commands written to it (ACK, id, reset) and switching to 4-byte packets after the IntelliMouse handshake. `haltest.Fake8042` gained an IntelliMouse on port 2. `sendkeys.py`: `mouse <dx> <dy>` and `click <button>` (QEMU monitor `mouse_move`, `mouse_button`). `user/mousetest.c` in `make devices-smoke`: classification, a left click at 612,434 after `mouse 100 50`, packets on `/dev/input/mice`, and `devices.screen` finds the cursor there. QEMU's window still has to grab the pointer for the PS/2 mouse to move (click into it; Ctrl-Alt-G lets go).

### [ ] W14-S03 select, and the small calls start-up code makes (E14)
`select` (23) and `pselect6` (270) over the same `Poller` code as `poll`. `pipe2` honours `O_NONBLOCK`. `getrandom` (318) and `/dev/random`, `/dev/urandom` (a ChaCha8 generator from Go's `math/rand/v2`, seeded from RDRAND when the CPU has it, else the TSC; not for cryptography, and documented so). `statx` (332, from the same data as `newfstatat`), `readlink`/`readlinkat` (`-EINVAL`: no symbolic links yet), `sysinfo` (99), `umask` (95), `getrusage` (98, zeros), `sched_getparam`/`sched_getscheduler` and `sched_setaffinity` (one CPU), `membarrier` (`-ENOSYS` is fine; checked). A `startup` test program calls each one and compares with Linux; POSIX_COVERAGE.md gains a row per call.

### [ ] W14-S04 A real-time clock (E14)
`drivers/rtc`: read the CMOS clock (ports 0x70/0x71, waiting out the update-in-progress bit, BCD and 12-hour forms) once at boot. `CLOCK_REALTIME` and `gettimeofday`'s source become boot wall time plus the monotonic clock; `clock_settime` stays `-EPERM`. `stat` times on `/tmp` and FAT writes use it, so files saved in `/home` get real dates. A host test with fake CMOS registers; on QEMU, `date` in busybox shows the host's date (`-rtc base=utc`).

### [ ] W14-S05 mmap of files (E14)
`MAP_PRIVATE` mappings of regular files at any page-aligned offset, read-only or writable (writes stay private), `PROT_EXEC` allowed, `MAP_FIXED` honoured; pages are filled from the file at first touch (an area with a backing file, `area.go`), and the part past the end of the file reads as zeros. Read-only `MAP_SHARED` of a file is treated the same; writable `MAP_SHARED` stays `-ENODEV` (documented). Works on every file system through `io.ReaderAt` (tarfs, memfs, FAT). fork copies these areas like any private memory. Tests: host tests in `kernel/proc`, and an `mmaptest` program that maps a file from `/`, `/tmp` and `/mnt`, checks the bytes and the zero tail, writes privately, forks, and unmaps.

### [ ] W14-S06 Unix sockets: socketpair (E14)
`socketpair(AF_UNIX, SOCK_STREAM | SOCK_DGRAM | SOCK_SEQPACKET)` with `SOCK_NONBLOCK` and `SOCK_CLOEXEC`; `read`/`write`/`readv`/`writev`, `sendto`/`recvfrom`, `sendmsg`/`recvmsg` (no control messages yet), `shutdown`, `MSG_DONTWAIT`, `MSG_PEEK`, `MSG_NOSIGNAL`; `EPIPE`/`SIGPIPE` and end of file like pipes; datagram boundaries kept; readiness for `poll`, `select` and epoll (`EPOLLRDHUP`). `getsockopt` `SO_TYPE SO_ERROR SO_RCVBUF SO_SNDBUF`, `setsockopt` of the buffer sizes. `fstat` reports `S_IFSOCK`. A `socktest` program checks each case against Linux.

### [ ] W14-S07 Unix sockets: names, connections and descriptor passing (E14)
`socket(AF_UNIX)`, `bind` (a socket node in a writable mount; `EADDRINUSE` while it exists, as on Linux, so servers `unlink` first), abstract names (a leading NUL byte, a per-system table), `listen` with a backlog, `accept`/`accept4`, `connect` (blocking, and `EINPROGRESS`-free: a Unix connect completes or fails at once), `getsockname`/`getpeername`, `SO_PEERCRED` (pid, uid 0, gid 0), `SO_PASSCRED` accepted. `SCM_RIGHTS` passes descriptors (the receiver gets new fds for the same open file descriptions; `MSG_CTRUNC` when the buffer is short); `SCM_CREDENTIALS` sent on request. `stat` and `ls -l` show the node as a socket; `unlink` removes it. `socktest` gains a client and server pair over `/tmp/sock` and over an abstract name, and passes a pipe end from one to the other.

### [ ] W14-S08 Graphics programs take the screen (E14)
The terminal calls full-screen programs make before they draw: `KDGKBMODE`/`KDSKBMODE` (`K_OFF` stops the console from taking keys while evdev readers are open; `K_RAW`/`K_MEDIUMRAW` deliver scancodes/keycodes through the terminal for servers that read the keyboard that way), `KDSETMODE` `KD_GRAPHICS`/`KD_TEXT` (the console stops and resumes drawing, as when `/dev/fb0` is open), and one virtual terminal: `VT_GETSTATE`, `VT_OPENQRY`, `VT_ACTIVATE`, `VT_WAITACTIVE`, `VT_GETMODE`/`VT_SETMODE`, with `/dev/tty0` and `/dev/tty1` naming the console terminal. `/dev/fb0` adds `FBIOGETCMAP`/`FBIOPUTCMAP` (accepted; 32 bpp truecolour has no palette) and `FBIOBLANK`. Every mode is undone when the process that set it exits, so a crashed program never leaves the console dead.

Exit: **M14 demo — desktop groundwork.** `make desk-smoke` boots `go-desk.img` and runs `mousetest`, `socktest`, `mmaptest`, `startup` and the `paint` demo, with screen checks; it joins `make test`. `make clean test` green; POSIX_COVERAGE.md covers every new call; DEVLOG wave entry.

Risks and pitfalls (PIT-NN entries go into BUGS_AND_MITIGATIONS.md when the wave starts):
- RAM above 4 GiB and the PCI hole are new for the PMM and the physmap: S01 tests both before anything relies on more memory.
- The mouse and keyboard share the 8042 and its data port: a byte read by the wrong side is lost. The driver must route by the status register's `stAux` bit, and the mouse must not start until the keyboard is set up.
- QEMU only sends PS/2 mouse motion while its window has grabbed the pointer (click into it; Ctrl-Alt-G releases). An absolute pointer (`vmmouse`, or a USB tablet) would remove the grab; it is a candidate for later, not this wave.
- Socket descriptor passing makes reference cycles possible (a socket sent over itself). Linux has a garbage collector for this; Burrow closes queued descriptors when the receiving socket closes and accepts the rare leak.
