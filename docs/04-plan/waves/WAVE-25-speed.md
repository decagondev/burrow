# W25 Cheaper Round Trips  (M25)  — status: in progress
Goal: a system call, and a wake-up from a blocking one, cost a fraction of what they do. Demo: `make lat-bench` shows each step of one round trip (gate, queue, dispatcher, handler, answer, resume) before and after, on Burrow and on the host's Linux; a clock read never leaves the program (a vDSO); `getpid`, a pipe ping-pong between two processes and a loopback TCP ping-pong are at least twice as fast as at the start of the wave; `scp` reaches 2 MB/s and NetSurf's first page comes sooner; X and NetSurf started as background jobs from the console draw (BUG-0033); burrow, not root, runs the desktop on the ext2 root; `make test` green. Stories: E22.F01-F05 ([BACKLOG.md](../BACKLOG.md)).

Where we start (after W24): every system call from ring 3 is a request the nucleus queues (`nucleus/uthread.c`: `post_and_wait`) and the Go kernel's dispatcher takes with `nu_syscall_wait`, starts a goroutine for (`System.Serve`, `go s.handle(r)`, then `runtime.Gosched`, BUG-0014), and answers with `nu_syscall_reply`, which wakes the user thread. `syslat` measures 126-161 µs for `getpid` on QEMU TCG (its limit is 500), and W24-S06 found what that costs: `scp` at 1 MB/s where TCP moves 5.5, with the cipher, the hash speed and dropbear's window ruled out (RISKS.md R-09). Clock reads are full round trips too: there is no vDSO, so musl's and Go's `clock_gettime` trap. Waits go through `reflect.Select` over a thread's channels (`kernel/proc/poll.go`). BUG-0033 is open: X and NetSurf as console background jobs make no progress while the foreground sleeps.

Design (measure, then shorten; the Linux ABI never changes):
- **Measure every step first.** A program times the round trips that matter (`user/lat.c`: `getpid`, a clock read, a pipe ping-pong between processes, a futex wake between threads, a socketpair and a loopback TCP ping-pong) on the host's Linux and on Burrow, and the nucleus stamps one request at each step with the TSC (kargs `lattrace`), so each change says which step it shortened. Nothing is optimised that was not measured.
- **What need not be a call is not one.** A vDSO, as Linux has: a page of code (`clock_gettime`, `gettimeofday`, `time`, `getcpu`) and a page of data the nucleus keeps current (TSC scale and offsets, written with a sequence count), mapped into every process and named by `AT_SYSINFO_EHDR`. musl and Go look for it on their own.
- **The dispatcher's path is short and allocates little.** One nucleus call answers a request and takes the next (`nu_syscall_reply_wait`), a thread's requests run on a goroutine that lives as long as the thread (no `go` per request), and calls that never block are answered on the dispatcher itself. Whatever changes keeps BUG-0014's lesson: the dispatcher must not sit on the only P.
- **A wake-up is a direct hand-off.** The path from "a pipe has data" to "the reader runs in ring 3" is measured on both sides (Go's channels and `reflect.Select`, the nucleus's `thread_wake` and its tick), and shortened where it waits: a cheaper wait than `reflect.Select` for the common one or two channels, and a woken thread that runs before the next tick. BUG-0033 is explained here, with its test.
- **Same results, measured twice.** Every slice runs `make test`; the budgets in `syslat`, `lat-bench`, `ssh-bench`, `browser-bench`, `net-bench`, `smp-bench` and `doom-bench` may only get stricter.

### [x] W25-S01 Measure the round trip (E22.F01)
`user/lat.c` (static musl): the round trips above, each a median of many, printed as `lat: <name> <us>`; it runs on the host's Linux (`make lat-linux`) and on Burrow. The nucleus stamps a request at the gate, when it is queued, when the dispatcher wakes, when Go takes it, when the handler answers and when the thread is back in ring 3 (`nucleus/lattrace.c`, kargs `lattrace=N`: N requests of one process, printed as `[lat] gate→queue ... resume` in µs). `make lat-bench` boots go.img with it and checks the numbers against `tests/smoke/lat-budgets.py`, set just above today's: the baseline every later slice is compared with. RISKS.md R-09 updated with the breakdown.
As built: the trace is a device rather than a kernel argument, so any program can ask for it: `/dev/lattrace` (`kernel/lattrace`, over `nu_lattrace` 0x102B) traces the call number written to it and reads back each step's average. The nucleus stamps a traced request at the gate (`nu_user_syscall`), when Go takes it (`uthread_wait`), when Go answers (`uthread_reply`), when the thread runs again (`post_and_wait`) and on its way out; the pure `nucleus/lattrace.c` sums the four steps (host-tested) and skips a request whose stamps are out of order. `user/lat.c` times the round trips as the median of seven batches (`make lat-linux` on the host: getpid 0.17 us, a clock read 0.02, ping-pongs 57-101 us under WSL). The baseline on Burrow (`make lat-bench`, four CPUs, seven boots): getpid 101-155 us, a clock read 110-164 (a full round trip: no vDSO), pipe 351-437, futex 116-211, socketpair 379-602, loopback TCP 1933-2713; getpid's steps on a quiet boot: gate to taken 14.5 us, taken to replied 68-70 (the Go side: two thirds of the trip), replied to resumed 16-17, out 1.4. TCG varies by half from boot to boot, so `tests/smoke/lat-budgets.py`'s budgets leave room (getpid 200, clock 220, pipe 600, futex 280, socketpair 900, tcp 3500). The first reads of `/dev/lattrace` came back as zeros one boot in three: BUG-0034, a Go stack array handed to a nucleus call could move before the nucleus wrote it; `raw` now carries `//go:uintptrescapes`.

### [x] W25-S02 A vDSO (E22.F02)
The nucleus keeps a data page (`nucleus/vdso.c`: TSC frequency, the monotonic and realtime offsets, a sequence count bumped around each update, `nu_set_realtime` included) and a code page built from `user/vdso/*.c` into a small ELF with Linux's names and versions (`__vdso_clock_gettime`, `__vdso_gettimeofday`, `__vdso_time`, `__vdso_getcpu`, `LINUX_2.6`); `execve` maps both into every process (read-only, the code executable) and puts `AT_SYSINFO_EHDR` in the auxiliary vector. Clocks the page cannot serve fall back to the system call. `user/vdsotest` (host and Burrow): the vDSO's clocks agree with the system call's, never go backwards across CPUs, follow `settimeofday`; `lat` shows a clock read in nanoseconds; `/proc/<pid>/maps` names `[vdso]` and `[vvar]`.
As built: the data page's layout is `include/burrow/vdso.h` (a sequence count, a ready flag, the TSC at monotonic 0, the multiplier and the realtime base: the same arithmetic as `time_monotonic_ns`); `nucleus/vdso.c` takes a zeroed frame for it and frames for the code at boot, before `time_init`, which publishes the clock, as `time_set_realtime_ns` does again (the RTC's one call). The code is `user/vdso/vdso.c` linked by `user/vdso/vdso.lds` into a 2.9 KB shared object (one page; `linux-vdso.so.1`, `LINUX_2.6`, plain and `__vdso_` names, both hash styles), position independent with no relocations (the Makefile refuses any), reaching the data page RIP-relative one page below itself; `nucleus/vdso_image.asm` carries it with `incbin`. `getcpu` reads `IA32_TSC_AUX`, which `percpu_bind` now sets to the CPU's index. `nu_vdso` (0x102C) tells Go the frames; `kernel/proc/vdso.go` maps `[vvar]` at `StackTop` and `[vdso]` one page above as device pages (never freed, shared by fork, mapped again by `execve`) and puts `AT_SYSINFO_EHDR` in the auxiliary vector. To make both paths one clock, the system call's monotonic clocks are now the runtime's `nanotime` (the nucleus's, from boot) instead of time since `kernel/proc` started; `TestClocks` checks it against the machine's clock. `user/vdsotest` passes on the host's Linux and on Burrow (`make ports-smoke`); a clock read is 85 ns on Burrow (21 on the host) where it was 110-164 us, and `gohello` shows Go's runtime finding the vDSO by itself. Clocks cannot be set on Burrow, so following `settimeofday` is the boot's one realtime change.

### [x] W25-S03 The dispatcher's path (E22.F03)
`nu_syscall_reply_wait` (a new nucleus call: answer one request and wait for the next in one crossing); a goroutine per user thread for its requests (started with the thread, ended with it; the requests of one thread were already one at a time); calls that cannot block (`getpid`, `gettid`, the id getters, `sched_yield`, `getrandom` of a little) answered on the dispatcher without a goroutine. Each change measured with `lat` and `lattrace`, kept only if it helps; `make test` with `SMP=1` and `SMP=4` (lock order, BUG-0014, BUG-0023's kills, signals and interrupt stops on a thread whose goroutine waits).
As built, each change measured with `lat` and the trace (getpid, quiet boots): the trace now also counts the Go kernel's own system calls while a user call is traced (`nu_lattrace` op 3, `go-call` lines). That found the first change, which the plan had not named: the Go kernel made 5.1 `clock_gettime` traps per user `getpid` (its scheduler's `nanotime`, `time.Now` in `enter`), so `go_load.c` maps the same vDSO into the Go kernel's address space and `go_stack.c` passes `AT_SYSINFO_EHDR` (the gate accepts the vDSO's code as a ring-0 caller, `go_vdso_lo/hi`): 0.14 calls per request after, but the Go side only fell from 64-70 to 64 us. The cost was the hand-off: `quick.go` answers the calls that never block (the id getters, `sched_yield`, the clock fallbacks) on the dispatcher itself, with no goroutine and no `Gosched` (and none at all when a batch is all quick), unless a signal is ready: getpid 103 to 64 us, the Go side 64 to 23. Then `nu_syscall_reply_wait` (0x102D): the dispatcher sends a quick answer with its next wait, one crossing instead of two, and blocks as it answers, so the woken thread runs at once: getpid 52-54 us, replied to resumed 19.6 to 8.1. `finish` split into `finishLeavingReply`. A goroutine per thread was not built: what the quick path removed is the hand-off between goroutines, which a long-lived goroutine would pay again on every request through its channel; the blocking calls' cost is the wait and the wake-up (a pipe read's trace: 124 us taken to replied, most of it the partner's turn), S04's subject. `blocking` now passes six arguments and carries `//go:uintptrescapes` too.

### [x] W25-S04 Wake-ups (E22.F04)
The path from an event (a pipe write, a socket's data, a futex wake, a timer) to the waiting thread back in ring 3, measured with `lattrace`; `poll`/`select`/`epoll`'s wait without `reflect.Select` when it waits on one or two channels; the nucleus runs a woken thread at once when its CPU is idle or running a lower-priority thread, not at the next tick. BUG-0033 explained and fixed, with its regression test (the failing console line as a smoke step). `lat`'s ping-pongs, `ssh-bench` and `browser-bench` re-measured.
As built: BUG-0033 was not a wake-up bug: the keys file's `wait demo: up` matched the echo of its own command (`echo demo: up''`, the `''` after the marker), so the screen was dumped before NetSurf started; it closed with `tests/smoke/keyslint.py` (in `sendkeys.py` and `make keys-lint`), which found six weak waits in existing keys files, fixed. The wake-up path, measured: the nucleus wakes promptly (an idle CPU polls 200 us for a kick, a halted one gets an IPI; a reply with the next wait hands the CPU over at once, 8 us); the cost is Go's. `lat` traces a pipe write too: 118 us from taken to answered for a write that never waits, the goroutine hand-off again. Answering writes on the dispatcher (an experiment) cut that to 47 us but stranded the reader woken by the write on the dispatcher's P while it waited in the nucleus (BUG-0014's shape), and the ping-pong got slower (340 to 392-409 us), also with a `Gosched` first: not kept. `poll`, `select` and `epoll` now wait through `waitAny` (`waitany.go`): a plain `select` over up to four files instead of building `reflect.SelectCase`s each time. Re-measured (TCG, four CPUs): `scp` 1.22-1.27 MB/s (1.0-1.1 before the wave's S03 and S04), a 4 MiB stream 1.25 MB/s, NetSurf's first page 2.71 s (3.52), the ping-pongs within noise of S01's. M25's targets for the blocking paths (ping-pongs twice as fast, `scp` at 2 MB/s) are not reached by what this wave planned; S06 sets the budgets from these numbers and RISKS.md says what is left: every blocking call still pays a goroutine hand-off.

### [ ] W25-S05 The desktop as a user (E22.F05)
What W24-S06 found on go-unix.img: TinyX starts only set-user-id root, and the X disk is FAT, which keeps no set-id bits. `scripts/mkroot.py` puts a set-user-id root copy of the X server on the ext2 root when the X disk is built (`/usr/bin/Xfbdev`, 4755), `startx` uses it; a login session gets the data disks' environment files (`/etc/profile` reads `x11.env` and `net.env` from the mounted disks); burrow runs `startx`, dwm, st and NetSurf, and `ps` over ssh shows them as burrow's. `make unix-desktop-smoke` (in `make test`; skips without `make x11 busybox net-ports browser`).

### [ ] W25-S06 M25
The budgets tightened from what S01-S05 measured: `syslat` (`getpid` well under its 500 µs limit), `lat-bench` (each ping-pong at least twice as fast as S01's), `ssh-bench` (`scp` at least 2 MB/s), `browser-bench`, `net-bench`, `smp-bench` and `doom-bench` no worse. Docs: an ARCHITECTURE.md section on the round trip (the steps, a sequence diagram, the numbers before and after), ADR-0012 for the vDSO and the dispatcher's shape, PORTING.md (what the vDSO gives programs), RISKS.md R-09 closed or re-scored; the DEVLOG wave entry.

Exit: **M25 demo — cheaper round trips.** `make lat-bench` prints the round trip's steps and passes budgets at least twice as strict as S01's for `getpid` and the ping-pongs; clock reads go through the vDSO; `scp` at 2 MB/s or more; BUG-0033 closed; burrow runs the desktop on the ext2 root; `make test` green on four CPUs and on one; DEVLOG wave entry.

Not in this wave: KVM or any change of emulator (the numbers stay TCG's), a new system-call ABI or batching that programs must ask for (io_uring), moving policy into the nucleus (only answers that need no policy: the vDSO's clocks), per-CPU run queues and an I/O APIC (E12 later), UEFI (the next wave), GTK.

Risks and pitfalls (PIT-NN entries go into BUGS_AND_MITIGATIONS.md when the wave starts):
- **TCG's numbers are noisy.** QEMU without KVM varies from run to run and with the host's load; medians of many round trips, budgets with room, and the same machine for before and after, or a change will seem to help when it does not.
- **A vDSO's clock must be the kernel's clock.** The page and the system call must agree to the nanosecond's rounding, never go backwards across CPUs (the TSC is invariant but each CPU's offset must match), and follow `settimeofday` without a torn read (the sequence count); Go's runtime calls the vDSO on its own threads too, so a bad page breaks the kernel's own clock.
- **A fast path skips work the slow path did.** Signals pending at return, interrupt stops, the CPU-time charge, a thread killed while queued (BUG-0023), `/proc`'s view of what a thread waits in: every path that answers a call must keep them, and the tests that cover them run on every change.
- **A goroutine per thread can leak or deadlock.** It must end with its thread on every path (exit, `execve`, kill, a process killed while blocked: BUG-0026), and it must not hold `s.mu` while it waits.
- **The dispatcher on the only P (BUG-0014).** With one CPU, Go has one P; a dispatcher that blocks in the nucleus without handing it over stalls every handler for sysmon's 2 ms. Each change runs `syslat` with `SMP=1`.
