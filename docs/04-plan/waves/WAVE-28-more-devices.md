# W28 More of a Real PC  (M28)  — status: in progress
Goal: the devices W27 left as "no driver" on a modern PC, each proved on QEMU first: an Intel 82574L network card (QEMU's `q35` default, the e1000e), USB hubs between xHCI and a device, Intel HD Audio, and an ACPI power-off and reset that hold on firmware that is not QEMU's. Demo: QEMU's `q35` with OVMF and its default devices, plus a USB hub carrying the keyboard, the mouse and the stick, an HD Audio controller with a codec and an NVMe disk: Burrow boots from the stick behind the hub, gets an address by DHCP on the e1000e, plays Doom with its sound through HD Audio, reboots by the FADT's reset register and powers off; the hardware report lists no PCI function a desktop needs as "no driver"; `make test` green. Stories: E25.F01-F05 ([BACKLOG.md](../BACKLOG.md)).

Where we start (after W27): on `q35` Burrow drives the I/O APIC and MSI, AHCI, NVMe, xHCI with keyboards, mice and sticks on the root hub's ports, and the stick boots the desktop. No real machine has reported yet (RISKS.md R-06), so this wave takes E24's "later" list, the devices nearly every PC of the last decade has and QEMU can emulate: the hardware report already names q35's own network card (8086:10d3) "no driver"; a keyboard plugged into a monitor's or a dock's hub would not be found; a PC has HD Audio, not AC'97; and power-off takes a sleep type found by a byte scan of the DSDT, with no switch into ACPI mode and no reset at all (the console's `reboot` is missing).

Design (each device proved on QEMU first; nothing W27 built changes shape):
- **The e1000e beside the e1000.** The 82574L keeps the 8254x's register map, legacy descriptors and interrupt causes; it differs in the EEPROM read register's layout, in having MSI and MSI-X, and in its PCIe extras the driver leaves at their reset values. `drivers/e1000` gets a model table (`8086:100E` 82540EM, `8086:10D3` 82574L) and drives every card it finds as `eth0`, `eth1`, ...; the 82574L takes MSI (its MSI-X needs the IVAR mapping a single queue does not). Host tests run the fake card as both models.
- **Hubs in `kernel/usb`.** A hub is a class driver (09.00): power its ports, read their status, reset a connected port and hand the device's speed to the host controller, which addresses it with a route string, its root port and, for a low- or full-speed device behind a high-speed hub, the hub's slot and port as its transaction translator. The host controller offers that through an interface a `usb.Device` may implement (`usb.HubHost`); xHCI also marks the hub's own slot as a hub (its port count, its TT think time). A status-change pipe reports later plugging and unplugging. Tiers up to five, as USB allows.
- **HD Audio as a second `sound.Output`.** `drivers/hda`: the controller reset, the CORB and RIRB rings in DMA pages for codec verbs, the codecs found by STATESTS, each codec's widget graph walked from an output pin back to a DAC, the path unmuted with its gain set, one output stream descriptor with a buffer descriptor list, and the stream's interrupt per buffer; `/dev/dsp` over it unchanged (OSS's ioctls, U8/mono converted). The pure parts (verb encoding, the widget walk, stream format words) host-tested against a fake codec.
- **ACPI that holds on real firmware.** Still no AML interpreter (ADR-0014's rule: only if a machine needs one): the switch into ACPI mode by `SMI_CMD`/`ACPI_ENABLE` when `SCI_EN` is clear, `\_S5` from the SSDTs as well as the DSDT and in every encoding a compiler writes (`ZeroOp`, `OneOp`, `BytePrefix`, `WordPrefix`), and a reset through the FADT's reset register, then port 0xCF9, then the keyboard controller; `reboot(2)` and the console's `reboot` use it.

### [x] W28-S01 The e1000e (E25.F01)
`drivers/e1000` drives the 82574L too (a model table; the EEPROM read register's shifted layout; MSI), every card it finds as `eth0`, `eth1`, ...; host tests run both models. `net-smoke` and `net-serve` once more with `NIC_MODEL=e1000e` (`make nic-smoke`), and `q35-smoke` boots a second time with `q35`'s own default card and gets its address by DHCP.

As built: `drivers/e1000`'s `Models` table (`regs.go`): the 82540EM (8086:100E) and the 82574L (8086:10D3), which reads its EEPROM through EERD with the word's address at bit 2 and done at bit 1 (the 8254x's are at 8 and 4); nothing else in the driver changed: the 82574L takes the same legacy descriptors (RFCTL.EXSTEN stays 0), causes and rings. `pci.Setup` gives it MSI (its MSI-X is left alone: one queue needs no IVAR mapping), and on a message the handler always claims, as xhci's does. The driver starts every card it finds, in PCI order, each as `netdev.RegisterNext`'s lowest free `ethN`, which virtionet now uses too, so a second card never renames the first (PIT-110). Host tests run the fake card as both models (`TestModelsReadTheirEEPROM`, `TestModelsMoveFrames`, `TestRegisterNextTakesTheLowestFreeName`). `make nic-smoke` runs net-smoke and net-serve on `-nic user,model=e1000e` with go-dev-dhcp.img; `q35-smoke` boots go-uefi-dhcp.img (kargs `net=dhcp`) on `q35` with no `-nic`, so on its own 82574L: DHCP, an ARP answer, `hw` naming the driver (`q35-e1000e.txt`). On `q35` the hardware report's "no driver" lines are now the host bridge, the LPC bridge and the SMBus controller only.

### [x] W28-S02 USB hubs (E25.F02)
`kernel/usb/hub.go` (the hub class: descriptor, port power, status, reset, the status-change pipe) over `usb.HubHost`, which `drivers/xhci` implements (route strings, the hub's slot context, transaction translators); host tests with a fake hub over a fake host. `usb-smoke-hub`: QEMU's `usb-hub` with the keyboard, the mouse and a stick behind it, and a second hub behind the first; go-smoke's keys typed through them, the stick's disk-smoke, a device pulled from the hub and plugged back.

As built: `kernel/usb/hub.go` (class 09): the hub descriptor, `HubHost.MakeHub`, every port powered and `bPwrOn2PwrGood` waited, each connected port reset (SET_FEATURE PORT_RESET until C_PORT_RESET, its change bits cleared, 10 ms recovery) and its speed from the port status handed to `HubHost.Attach`; the device is bound by `usb.Connect` (`attach.go`), which also serves the root ports now, so a hub's devices get the same log and report line with a dotted path (`port 5.2.1: ...`). A goroutine reads the status-change endpoint: a connection change detaches the old device and attaches the new one (`port 5.3: disconnected` in the log and the report). Five tiers at most; a USB 3 hub's SuperSpeed half is reported, not driven (its USB 2 half carries keyboards and mice). `drivers/xhci/hub.go`: `*Device` is the `HubHost`: the slot context (`context.go`'s `slotInfo`) carries the route string, the root port, the transaction translator (the nearest high-speed hub's slot and port, for a low- or full-speed device: `childPlace`, PIT-107) and, for a hub, Hub, its port count and TT think time (Configure Endpoint with the slot context alone); `enumerate` is shared by root ports and hub ports; `release` detaches what is below, closes the device's `gone` channel (an interrupt pipe's wait ends with an error) and gives the slot back (Disable Slot). Host tests: a fake hub as its own host (`TestHubEnumeratesItsPorts`, `TestHubHotPlug`, the SuperSpeed and no-host cases), route strings, TT placement and hub slot contexts. `usb-smoke-hub` (in `make usb-smoke`): QEMU's usb-hub (full speed, so no TT on QEMU) on root port 5 with the keyboard, a second hub carrying the mouse, and a stick; the console is typed and mousetest driven through them, the stick's volume read at `/mnt`, then the stick pulled and a second one plugged into the same port (`ubb`). The stick's disk-smoke stays on root ports (`usb-smoke-storage`): a hub changes how a device is addressed, not its transfers.

### [x] W28-S03 Intel HD Audio (E25.F03)
`drivers/hda`: controller reset, CORB/RIRB, codec discovery and the widget walk to a line-out or speaker pin, one output stream with a BDL ring, `/dev/dsp` as for the AC'97 (one card is `/dev/dsp`, a second `/dev/dsp1`); host tests against a fake controller and codec. `sound-smoke` and `doom-smoke`'s recording once more on `-device intel-hda -device hda-output` (`make hda-smoke`), checked by `checkwav.py` as before; `ich9-intel-hda` on `q35`.

As built: `drivers/hda` (driver `hdaudio`: `hda` is an IDE disk's name), class 04.03: `ctl.go` resets the controller (CRST), reads STATESTS for the codecs and runs the CORB and RIRB (256 entries each in one DMA page, polled; RIRBCTL's response flag on and RIRBSTS cleared after each response, since QEMU's controller stops after RINTCNT responses until it is cleared); `codec.go` reads the audio function group's widgets (capabilities, connection lists in both forms with ranges, pin capabilities and configuration defaults) and searches from the best connected output pin (line out, speaker, headphones) through mixers and selectors to a DAC, never by fixed node ids (PIT-108); `path.go` powers the path, selects connections, unmutes amplifiers at their 0 dB step, enables the pin (headphones, EAPD) and gives the DAC the stream tag and format, with format words for 8-96 kHz from the converter's PCM parameter. `stream.go` is the `sound.Output`: 32 pages in a BDL the controller plays round and round, each with its completion interrupt; played pages are zeroed, positions are LPIB from just after the stream started, and with nothing queued the stream stops and resets, clearing RUN with its stream number kept. Registers are read and written at their own width and offset (`MMIO`). `/dev/dsp`, or `/dev/dsp1` beside an AC'97; the codec's id and its path go into the log and the hardware report's claim (`codec 0 1af40012, pin 3 (line out) <- dac 2, msi line 16`). Host tests against a fake controller and a codec with decoys (an unconnected line out, a speaker that reaches no DAC); the stream test checks the stream number a stop carries. `make hda-smoke`: tone on `intel-hda` (pc) and `ich9-intel-hda` (q35, OVMF), each recorded and measured (440 Hz at 48 kHz, 880 Hz after the change to 22050 Hz), and doom-smoke's sounds recorded on `intel-hda`.

### [x] W28-S04 ACPI power-off and reset (E25.F04)
`nucleus/acpi.c`: ACPI mode on by `SMI_CMD` when the FADT says the firmware has not, `\_S5` from every SSDT and in each AML integer encoding (unit tests over hand-built tables and QEMU's own DSDTs for `pc` and `q35`), the FADT's reset register; a reset call (`nu_reset`) with 0xCF9 and the 8042 as fallbacks; `reboot(2)` with `LINUX_REBOOT_CMD_RESTART` and the console's `reboot`. `make reboot-smoke`: busybox `reboot` and the console's on `pc` and `q35`, QEMU's reset seen as a second boot.

As built: ACPI mode was already switched on through `SMI_CMD` before a power-off (W20-S04). `nucleus/acpi.c` now also looks for `\_S5` in every SSDT when the DSDT has none, reads each integer encoding (Zero, One, Ones, Byte-, Word-, DWord- and QWordPrefix; a one-element package gives both types) and the FADT's reset register when `RESET_REG_SUP` is set (I/O, memory or PCI configuration space); three new unit tests. `acpi_reset` (`acpi_boot.c`) tries the reset register, port 0xCF9, the 8042's reset pulse and a triple fault (`cpu_triple_fault` in `cpu.h`), each announced first (`[nucleus] reset: ...`, PIT-109); `nu_reset` 0x1030 takes the way to start from. At boot the nucleus says what it found (`acpi: reset register io cf9 = f`, or `no reset register`, and `S5 from an SSDT`). Go: `amd64.Reset`; `kernel/proc/reboot.go` serves `reboot(2)` (magic numbers, root only: RESTART, POWER_OFF, HALT powering off, CAD on and off accepted) and `kill` of PID 1 with busybox init's signals (SIGTERM restart, SIGUSR2 power-off, SIGUSR1 halt), both to the kernel's `SetPower` action (`cmd/kernel/power.go`), and `sync`/`syncfs` succeed with nothing to do; the console's `reboot [register|cf9|kbc|triple]`; busybox gets `reboot`, `poweroff` and `halt`. `smoke.sh`'s `ALLOW_REBOOT=1` leaves out `-no-reboot`. `make reboot-smoke`: go-busybox.img on `pc` (no FADT reset register: 0xCF9) restarted by the console, busybox's `reboot` and `reboot -f`, then from the keyboard controller and from a triple fault, then powered off by busybox's `poweroff`, six boots in one run; go-uefi.img on `q35` restarted through its FADT's reset register (I/O 0xCF9 = 0x0F) and OVMF.

Not in this wave: Realtek cards (QEMU has no r8169 to prove one on), the 82576 `igb` and newer Intel cards (I210, I219: their PHY and power-gating need a real card), Wi-Fi, EHCI and OHCI/UHCI controllers (xHCI serves every USB 2 and 1.1 device through its own ports and through hubs), USB audio, HDMI audio and microphones (output only), an AML interpreter, suspend and resume, a GPU driver.

Risks and pitfalls (PIT-NN entries go into BUGS_AND_MITIGATIONS.md when the wave starts):
- **A hub's speeds mix.** A full- or low-speed device behind a high-speed hub talks through the hub's transaction translator, which the slot context must name; QEMU's `usb-hub` is a full-speed hub and needs none, so the TT fields are host-tested only.
- **HD Audio codecs differ more than controllers do.** The widget graph, pin defaults, amplifier capabilities and EAPD vary per codec; QEMU's `hda-output` is the simplest graph there is. Walk the graph from pin defaults, never fixed node ids, and put the codec's ids and the chosen path in the hardware report.
- **ACPI mode and reset differ per firmware.** Some firmware boots in legacy mode until `ACPI_ENABLE` is written; some reset registers live in memory, not I/O space; some machines ignore 0xCF9. Try in order and print what each step did on the screen before the machine goes away.
- **A second network card changes names.** `eth0` must stay the first card the boot found, in PCI order, so `/etc/net.conf` keeps meaning the same card.
